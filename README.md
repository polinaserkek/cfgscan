# cfgscan

`cfgscan` — CLI-утилита для анализа конфигурационных файлов веб-приложений и выявления потенциально опасных настроек.

Утилита принимает YAML/JSON-конфигурацию, преобразует её во внутреннюю модель и выполняет набор проверок безопасности.

---

# Возможности

Поддерживается:

- YAML и JSON конфигурации;
- чтение из файла;
- чтение из стандартного потока (`--stdin`);
- набор независимых правил проверки;
- вывод найденных проблем с уровнем критичности;
- рекомендации по исправлению;
- управление кодом завершения через `--silent`.

---

# Запуск

## Проверка файла

```bash
go run ./cmd/cfgscan path/to/config.yaml
```

Пример:

```bash
go run ./cmd/cfgscan testdata/example.yaml
```

Чтение из stdin

```bash
cat config.yaml | go run ./cmd/cfgscan --stdin
```


## Отключение ошибки при найденных проблемах

По умолчанию при наличии найденных проблем программа завершает работу с кодом 1.

Чтобы использовать утилиту в режиме проверки без ошибки завершения:

```bash
go run ./cmd/cfgscan --silent config.yaml
```

Также доступен короткий вариант:

```bash
go run ./cmd/cfgscan -s config.yaml
```


В текущей реализации используется демонстрационная схема конфигурации.

Проверяются следующие поля:

- log.level: уровень логирования
- storage.digest-algorithm: используемый алгоритм хеширования
- auth.password: наличие пароля в открытом виде
- tls.enabled: состояние TLS
- network.address: адрес прослушивания приложения


Пример конфигурации:

```yaml
version: 1

log:
  level: debug

storage:
  digest-algorithm: md5

auth:
  password: admin123

tls:
  enabled: true

network:
  address: 0.0.0.0

```


# Принятые допущения

Тестовое задание не определяет единую схему входного конфигурационного файла.

Например, не указано:

- где именно хранится настройка TLS;
- как представлен пароль;
- каким полем задается адрес прослушивания;
- каким образом описывается алгоритм хеширования.

Поэтому в реализации используется демонстрационный формат конфигурации, содержащий поля, необходимые для проверки заданных правил.

Данное ограничение относится только к структуре входного файла и не влияет на архитектуру приложения.

При необходимости поддержка новых форматов или схем конфигурации может быть добавлена через расширение слоя парсинга и модели конфигурации.

Также проверка выполняется только для известных устаревших алгоритмов (MD5, SHA-1). Неизвестные алгоритмы не классифицируются как небезопасные.

# Архитектура

## Основной поток обработки:

Config file -> Parser -> config.Config -> Scanner + Rules -> []Issue -> CLI output


## Основные компоненты:

internal/
- /config: структуры конфигурации
- /issue: модель найденной проблемы
- /parser: преобразование YAML/JSON в Config
- /rules: отдельные проверки безопасности
- /scanner: запуск набора правил


# Расширение правил

Сканер построен на основе интерфейса Rule.
Добавление нового правила не требует изменения существующей логики анализа.

Интерфейс правила:

```go
type Rule interface {
	Check(cfg config.Config) []issue.Issue
}
```

Для добавления нового правила:

1. Создать новую структуру в пакете internal/rules.

Пример:

```go
type ExampleRule struct{}
```

2. Реализовать метод Check:

```go
func (e ExampleRule) Check(cfg config.Config) []issue.Issue {
	// логика проверки

	return nil
}
```

3. Добавить правило в список проверок сканера:

```go
func New() Scanner {
	return Scanner{
		checks: []rules.Rule{
			rules.DebugRule{},
			rules.MD5Rule{},
			rules.PasswordRule{},
			rules.TLSRule{},
			rules.OpenBindAddressRule{},
			rules.ExampleRule{},
		},
	}
}
```

После регистрации правило автоматически будет выполняться при анализе конфигурации.



# Уровни критичности

Тестовое задание явно задает уровни критичности только для примеров с debug-логированием и MD5.

Для остальных случаев уровни выбраны исходя из потенциального влияния проблемы на безопасность приложения.


**HIGH**

- Пароль хранится в открытом виде: Может привести к компрометации учетных данных.

- TLS отключен: Данные могут передаваться без необходимого уровня защиты.

- Использование небезопасных алгоритмов: Например, MD5. Может снизить надежность защиты данных.



**MEDIUM**

- Использование 0.0.0.0 в качестве адреса прослушивания: Не всегда является ошибкой (например, для публичных сервисов), но расширяет область доступности приложения и потенциальную поверхность атаки.


**LOW**

- Debug-режим логирования: Не является критической уязвимостью, но может привести к раскрытию служебной информации в логах.
